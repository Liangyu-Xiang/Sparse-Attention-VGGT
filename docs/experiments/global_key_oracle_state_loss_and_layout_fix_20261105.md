# 状态损失、全局Key oracle与候选布局修复（2026-11-05）

这轮按用户澄清的定义，在全局Key预算内联合搜索所有cluster需要的Key，绝不预设每簇保留一个Key。每簇的数量和成员集合都是联合搜索的结果。

## 结论

1. 查到并修复一个实际实现错误：Exact候选mask为列连续，但Triton按行连续读。旧pipes层6/group12实际执行129个逻辑上不允许的整簇支持；eager与Graph同样复现，386个不允许的Exact状态被赋有限损失。修复直接改变分配器读取的候选，不是更换方法。
2. 状态损失定义也不自洽。History={Rep}时两状态支持/权重/成本完全相同，但代理损失不同。真实74,592个cluster-case中29,833个满足该边界，29,504个损失不同。精确概率反例证明Rep损失为0不代表归一化输出误差为0。
3. 全局oracle显示概率估计、损失/全局相互作用及状态表达能力同时存在问题。只把目标改成联合归一化损失、保留估计概率，并没有改善实际输出；不能凭公式看起来更接近输出就采用。
4. 新bug意味着之前“没有发现支持约束实现错误”的判断已被本轮证据更新。改变簇数量也会改变错误mask的排列，旧参数消融不能当作普适根因结论。

## 全局oracle的范围和含义

使用修复后方法的冻结QKV/聚类/History。在ETH3D pipes、playground、courtyard各取Global层6/11/13/19、2个Query组；每组全部稀疏执行Query、所有patch Key、所有cluster、全部head和完整Wo参加损失。每张mask的patch Key总上限等于native实际用量，保护Key不变；自由Key算子也使用cluster_population权重，因此预算和执行规则没有放宽。

- 真实概率+原损失：仅替换概率，冻结历史资格、特征、候选、成本和执行。
- 同特征联合目标：仍使用原head-mean特征及估计概率，改为全局softmax归一化后的输出损失。
- 完整Wo联合目标：保留估计概率，改用完整Value/head与Wo。
- 状态oracle：用真实当前QK评估整张mask的输出误差，仍受原四状态限制。
- 自由Key oracle：同样的真实全局目标，可以任意选择各簇内的成员和数量，不预设配额。

Oracle是40步离散straight-through搜索的已发现最优结果。状态oracle使用2个起点，自由Key用3个起点（含状态oracle支持），逐步保持全局预算可行；不是穷举全局最优，也不是唯一必须保留的Key集合。它只用于诊断，不放入推理、不使用几何真值。

完整表格、曲线、原始全局case及每簇Key集合见 [report](../../outputs/global_state_loss_oracle_20261105/report.md)。每个场景的`clusters.jsonl.gz`含全部簇的native/oracle Key列表、数量、Rep、History资格、四状态损失和成本。Key为patch域编号；当前配置未保护首帧patch，若每帧P个patch，则全局token编号为floor(k/P)*(P+5)+(k mod P)+5。

## 为什么现有状态没有选到oracle支持

pipes层11/group12的簇0有11个成员：native为Rep={153}，全局oracle需要{0,85,224}；合格History={0,3,153,224}，Exact不允许。

- Key85根本不在任何可用状态中，当前状态无法精确表达这组3-Key支持。
- Rep代理损失0.000741338、成本1，History损失0.001096850、成本4：代理损失及预算价格都偏好Rep。
- 使用真实全局输出目标时，受四状态限制的联合搜索改选History，但仍含多余Key且缺85；自由Key搜索可进一步改善。
- 同一全局搜索又让簇116从12-Key Exact变为0个Key，说明这是全局预算重分配，不是局部单Key选择。

全局统计中，所找到自由oracle的Key有31.66%–43.86%不在任何当前可用状态内。即使对所有簇开放Exact，要完整覆盖该oracle集合的最小Key成本仍平均为预算的2.68–4.20倍。这证明当前状态不能表达该集合，不证明所有其他四状态mask都不可能取得同等输出误差。

## 修复与速度边界

实现只修改候选mask分配布局以及状态kernel的stride读取。直接分配行连续mask，不增加每窗口copy，也不增加QK、保留率或网络层数。新增普通/bounded两种转置mask回归测试通过，原CPU代数和CUDA Graph验证通过；共核查修复前后48个冻结selector行，其中24个修复后行的实际支持均符合可用状态与候选限制。

质量只复核ETH3D三个诊断场景（3/11），完整六指标和3场景等权均值在报告中；它不是完整ETH3D最终评测。修复前后的F1：pipes 34.40%→78.47%，playground 19.59%→27.02%，courtyard 41.07%→56.69%。剩余退化仍明显。

速度仅测7Scenes heads128，GPU6同卡独占，1暖机+3次完整前向中位数。所有Oracle/内核诊断六指标N/A附原因；ETH3D缺少配对Dense暖机计时，加速N/A；计时控制不重跑几何质量。
